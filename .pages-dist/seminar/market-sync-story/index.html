LuckyStock AI Seminar Sample

배치가 멈췄고, 운영 체인을 다시 설계해야 했습니다

이번 페이지는 LuckyStock의 market sync 복구 작업을 스크롤 발표 형식으로 정리한 샘플입니다. 왜 이 작업이 시작됐는지, 어떤 프로그램을 사용했는지, 실제 운영 경로가 어떻게 바뀌었는지 한 화면에서 설명하도록 구성했습니다.

문제 발생일: 2026-03-26 복구 완료일: 2026-03-27 배포 형식: URL 발표 페이지
운영 세션 `tmux market-sync`
핵심 복구 launcher -> autostart -> watchdog -> supervisor -> loop

1. 만들게 된 계기

문제는 배치 실패가 아니라 감시 체인 전체 정지였습니다

처음에는 단순히 market sync 배치가 한 번 실패한 것으로 보였지만, 실제로는 watchdog, supervisor, loop 프로세스가 모두 stale 상태로 남아 있었습니다. 즉, "한 번 죽은 뒤 자동 복구가 되지 않는 구조"가 핵심 문제였습니다.

  • 마지막 heartbeat는 2026-03-26 10:01 UTC에서 멈춤
  • PID 파일은 남아 있었지만 실제 프로세스는 종료된 상태
  • 기존 서버에는 `cron`, `systemd`가 없어서 일반적인 복구 방식이 통하지 않았음

3. 사용 프로그램

이번 복구에 직접 사용한 프로그램과 도구

LuckyStock AI

실제 운영 대상 서비스. KRX, 네이버, 뉴스, 정적 페이지 배치를 연결하는 메인 프로젝트입니다.

tmux

`cron`과 `systemd`가 없는 환경이라 detached session으로 launcher를 영구 실행하는 용도로 사용했습니다.

Node.js Batch

`build-stock-master`, `market-sync`, `sync-pages-dist`, `deploy-pages` 같은 배치 스크립트 실행 엔진입니다.

SQLite Fallback

KRX가 403을 반환할 때 기존 `stock_master`를 fallback 데이터원으로 사용해 배치 중단을 막았습니다.

4. 사용 경로

실제 코드와 운영 경로는 어디에 있는가

발표 페이지 경로 /seminar/market-sync-story/

최상단에서 autostart 프로세스를 감시하고 재시작하는 시작점

KRX 차단 시 SQLite fallback을 제공하는 공통 유틸

가격 배치 /scripts/build-stock-master.mjs

실시간 가격 수집과 stock_master 갱신 담당

운영 세션

`tmux` 세션 이름은 market-sync 입니다.

복구 방식

세션이 살아 있는 동안 launcher가 하위 프로세스를 계속 복구합니다.

데이터 안정성

KRX 403 발생 시 SQLite fallback으로 master 목록을 읽어 배치 연속성을 유지합니다.

6. 검증 결과

복구 후 확인된 상태

  • `tmux ls` 기준 `market-sync` 세션 실행 중

  • `build-stock-master`는 KRX 403 이후 SQLite fallback으로 정상 완료
  • 최종 로그: `upserted=2624, priced=2624/2624`
